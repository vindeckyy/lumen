# Known limits

Lumen is not finished. M0 is complete. M1 through M8 are not. Nothing in this file is a latency result. Items are grouped by what blocks the next milestone.

Blocker status: B1 (P-frame decode) is closed. B2 (DMA-BUF contract) is closed. B3 (media pipeline) is largely done: the host pipeline and the client pipeline exist, and a run was measured.

## Blockers for M1

- **B1. P-frame decode: closed.** `lumen-decode-vaapi` decodes P slices. `crates/lumen-decode-vaapi/src/dpb.rs` holds the decoded picture buffer: frame_num gap check, POC types 0 and 2 (type 1 only for an IDR), sliding-window marking, list 0 in descending `FrameNumWrap`, and state changes committed only after a picture decodes. `crates/lumen-decode-vaapi/src/bitstream.rs` parses I and P slices, `num_ref_idx_active_override`, `pred_weight_table`, `cabac_init_idc` and `dec_ref_pic_marking`. The round trip in `crates/lumen-decode-vaapi/tests/roundtrip.rs` decodes 30 frames at 1280x720, an IDR plus 29 P frames, with luma PSNR min 47.60 dB and mean 50.47 dB and no decode errors. Encoder output can now be decoded end to end.
- **B2. DMA-BUF contract: closed.** `DmabufImage` in `crates/lumen-protocol/src/media.rs` carries the fd, the DRM fourcc, the format modifier and up to `MAX_DMABUF_PLANES` (4) planes, each with its own offset and stride. `DRM_FORMAT_MOD_LINEAR` and `DRM_FORMAT_MOD_INVALID` live in `lumen-protocol` (D38, D39). The radeonsi tiled NV12 layout, modifier `0x0200000000000901`, with UV at a different pitch and offset from Y, is now expressible. The consumer that is still missing is the renderer, which cannot import NV12 (O-7).
- **B3. Media pipeline: largely done.** The host pipeline is `crates/lumen-host-service/src/pipeline.rs`, with the binary `lumen-host`. The client pipeline is `crates/lumen-client-desktop/`, with the binary `lumen-client`. The host captures a wlroots output, converts it to NV12 on the CPU, encodes it with the VA-API H.264 encoder, slices and seals the access units and sends them over UDP. The client reassembles the slices, decodes with VA-API, converts to BGRX and presents through Wayland or X11. A run was measured: 1280x720 at 30 fps over loopback and over the network namespace pair. Every access unit that was delivered was decoded and presented with zero decode errors, and the namespace run lost zero packets. The frame counts vary with the load on the machine; read them from `artifacts/m1/e2e.json` and `artifacts/m1/e2e-netns.json`. These are software counters, not glass-to-glass. The per-stage latency percentiles are now recorded, so the pipeline latency can be read out of the run report: the 30 second loopback run in `artifacts/m1/e2e.json` gives a software pipeline latency from capture to present of p50 23.52 ms, p99 27.37 ms and max 51.18 ms over 872 samples, and the namespace run in `artifacts/m1/e2e-netns.json` gives p50 23.50 ms and p99 27.92 ms. That is still a software counter and not a glass-to-glass number: it excludes the display's own scan-out and the camera path, and the two clocks are aligned by the offset the host estimates from the ping exchange (O-25). The NACK path has still never been exercised, because the measured runs never needed one: the FEC rebuilds every frame that is missing a slice (O-19). The adaptive parity and the link feedback now make the loss visible to the host, so the parity level rises when the link gets worse (D69). The per-stage numbers also say where the time goes. Measured on this machine at 1280x720, the CPU `bgrx_to_nv12` takes 2.52 ms and `nv12_to_bgrx` takes 3.57 ms, so the client's present stage (p50 4.52 ms) is mostly the colour conversion, and the host's capture stage (p50 8.23 ms) holds that same conversion plus the DMA-BUF readback. Moving the colour conversion to the GPU is the largest single latency win left (D49, O-7).
- **B4. No photodiode rig and no second machine.** Unchanged. The harness has the barcode, the recorder, the report, a simulated trigger and the `lumen-bench rig-selftest` subcommand. There is no camera rig and no second machine, so glass-to-glass cannot be measured here. The `harness/` directory with the rig procedure and the camera capture loop does not exist (O-22).

- **O-17 (closed). The FEC policy is adaptive.** The parity level follows the measured loss: no parity below 0.5 %, two parity slices per block of eight data slices below 2 %, three per block of twelve at or above it. The heavy level uses twelve data slices so three parity slices stay inside the 25 % overhead cap. The block size travels in the header's `flags` word, so the receiver maps a slice index to its block without being told the level. Three losses inside one block are recoverable: the three parity equations are a Vandermonde system over GF(256) solved by Gaussian elimination. See D59 and D60.
- **O-18 (closed). The estimator drives the encoder.** The client reports the slices it received and lost and the round trip time of the control channel; the host differences the cumulative counts into the estimator, and the estimator's target rate is pushed into the encoder's constant bitrate. libva carries the rate in a misc-parameter buffer, so the encoder recreates that buffer when the rate changes. The rate only reaches the encoder when it runs in constant bitrate mode: a constant quantiser has no rate to set. See D62.
- **O-19 (closed). The NACK path is wired and bounded.** The host answers a NACK: `ControlStage::run` in `crates/lumen-host-service/src/pipeline.rs` turns a `ControlMessage::Nack` into an `EncodeCommand::Retransmit`, and the encode stage calls `MediaSender::retransmit`, which seals the slice again with a new sequence number. The client has the other half: `ReceiveStage::run` in `crates/lumen-client-desktop/src/receive.rs` reports the slices that `MediaReceiver::missing` still lacks for the previous frame when a new frame starts, that is when the first data slice of the next frame arrives. Both halves are implemented, but no measured run has produced one. The loss sweep is the first run over a genuinely lossy link, and it shows `nacks_sent` 0 and `retransmits` 0 at every level, because the FEC recovers the frame before a NACK is needed: the access units fit in one data slice, so every frame is one data slice plus two parity slices, and the parity rebuilds the data slice on its own. `RetransmitQueue` in `crates/lumen-transport/src/retransmit.rs` is still unused, so the retransmit deadline does not bound the resend: the host resends whatever slice the NACK names.
  - Where: `crates/lumen-host-service/src/pipeline.rs`, `ControlStage::run` and `EncodeStage::run`; `crates/lumen-client-desktop/src/receive.rs`, `ReceiveStage::run`; `crates/lumen-transport/src/retransmit.rs`; `crates/lumen-host-service/src/control.rs`, `ControlMessage::Nack`; `crates/lumen-transport/src/media.rs`, `MediaSender::retransmit`.
  - The deadline is the frame's capture timestamp plus 1.5 frame intervals: past it the host does not resend, and the client drops the frame and asks for a keyframe. The policy lives in `crates/lumen-transport/src/nack.rs` and the deadline check in `StageRecorder::may_retransmit` in `crates/lumen-host-service/src/stages.rs`. The measured runs still never need a NACK, because the parity rebuilds the frame first; see O-26. See D63.

- **O-25. The clock offset estimate assumes the two directions take the same time.** The host aligns the two clocks with an NTP-style estimate: it pings the client, the client answers with its own clock reading, and the host takes the offset as the client's reading minus the midpoint of the round trip. On a LAN the error is small, and in the measured runs it is bounded: the `send` stage's minimum is positive in the current artifacts, which cannot happen on the wire if the client stamped `recv` before the host stamped `send`. ## Closed defects

Each entry was open at the last handoff and is closed now. It stays here so the history is not lost.

- **G2. Parity-only frames are never recovered: fixed.** The parity arm of `SliceAssembler::push` in `crates/lumen-transport/src/slice.rs` now creates the frame state before it stores the parity, so `try_recover` has a frame to recover into. The test `single_slice_frame_recovers_from_parity_alone` in `crates/lumen-transport/src/media.rs` covers it: with `ParityLevel::Light` a 300-byte access unit is packetised, the only data slice is dropped, and the frame is rebuilt from the two parity slices.
- **O-1. Pairing is not enforced: closed.** The host now refuses a client it does not trust unless the client answers the pairing code. `crates/lumen-host-service/src/pairing.rs` holds the host's long-term Ed25519 identity key and the public keys of the clients it trusts in a JSON store file, and `crates/lumen-host-service/src/session.rs`, `host_hello`, sends a `PairingChallenge` and checks the answer. The client proves ownership of its identity key by signing a host nonce: the message it signs binds the host key, the client key and the nonce, so a claimed public key alone proves nothing and a proof cannot be replayed into another session. `HelloAck.paired` now reports the truth. See D52.
- **O-5. Protocol doc drift: closed.** `docs/protocol.md` section 3 describes the 42-byte header of `crates/lumen-protocol/src/header.rs`, section 7 describes the Noise frames and the encrypted control records, and section 2 no longer lists a `magic` field for `Hello`.
- **O-6. Media peer address is not negotiated: decided.** This is a decision, not a protocol change. The host sends media to the IP address of the control connection's peer, on a fixed client media port, 24801 by default and set with `--client-media-port`. The control connection already proves the peer's address, and the LAN-only threat model does not need a handshake field for it. The consequence is that the media port cannot vary per client: a host serves one client media port at a time. See D50.
- **O-8. Encoder DMA-BUF import unverified: closed.** The test `crates/lumen-encode-vaapi/tests/dmabuf_import.rs` imports a DMA-BUF that VA-API itself exported, with the AMD tiled modifier `0x0200000000000901` and two planes, and the encoder produces an IDR from it. It passes on `renderD129`.
- **O-21. Missing repo basics: closed.** `README.md`, `LICENSE-MIT`, `LICENSE-APACHE` and `.github/workflows/` exist. `ci.yml` runs fmt, clippy `-D warnings`, the workspace tests, `cargo deny` and `cargo audit`; `fuzz.yml` runs the fuzz smoke.

## Paths compiled but not exercised

- **EIS (libei).** No EIS server is installed and sway does not implement EIS, so `lumen-ffi-libei` and `lumen-input-wayland::EisSource` compile but never talk to a server. Event decoding is untested.
- **Portals.** The PipeWire daemon is running and `xdg-desktop-portal` with the wlr backend is installed, but the ScreenCast, InputCapture and RemoteDesktop consent flows are untested. Consent is needed the first time. Restore tokens are not implemented. The audio path does use PipeWire, but through a virtual sink the session creates itself, not through the portal.
- **DRI3 capture.** Opt-in only (D7). The default ladder walks MIT-SHM then GetImage; `LUMEN_X11_TEST_BACKEND=dri3|shm|get` forces a rung. Forced DRI3 on Xwayland produced `frame 796x573 dmabuf fourcc XR24 modifier 0x0 planes 1`. Reading before the fence completes returns zeros.
- **wlroots `copy_with_damage`.** The path exists and is unit-tested, but the live run reported `damage_copy=false`, so it was not exercised. Headless sway reports refresh 0 mHz, so the live test prints a skip. The refresh-rate trigger is untested (O-12).
- **wlroots fence behaviour.** The DMA-BUF frame assumes the `ready` event means the copy is finished. The GPU side was not checked (O-11).
- **Render DMA-BUF presentation.** The `linux-dmabuf` path (linear XR24 via gbm on `renderD129`) is implemented, and the three Wayland tests passed under sway in an earlier run. Decoded NV12 still cannot be presented (O-7).
- **X11 composite unredirect.** Xvfb rejects `UnredirectWindow` without a compositor. The result is reported through `is_unredirected()`. Not checked on a real compositor.
- **uinput.** `crates/lumen-input-inject/src/uinput.rs` uses evdev 0.13 and has a narrow test against a real device. Devices are created under sudo. `uhid` gamepad support is not present.
- **XTEST.** Only absolute motion is exercised, which is what the latency measurement uses. Keys, buttons, scroll and pointer lock are not.
- **Wayland seat fallback.** Only the skip path ran. The live path was not tested in that session.
- **X11 input.** `crates/lumen-input-x11` is implemented: XI2 raw motion, key press and release, with the keymap through xkbcommon. The measured latency is the injection leg only, because the input path is not wired into the host service.
- **Wayland input extras.** The EIS source is implemented but not exercised live. IME (`zwp_text_input`), relative pointer, pointer constraints, touch, pen and gamepad client capture are open. Verify which of these `crates/lumen-input-wayland/src/` really has before planning the work.

## Hardware coverage on this machine

- VA-API H.264 decode is verified for a 30-frame 1280x720 round trip (an IDR plus 29 P frames, luma PSNR min 47.60 dB, mean 50.47 dB) and separately for a flat CABAC IPPP x264 stream that decodes exactly as ffmpeg does (Y 126, UV 128 in all four frames). Not verified: CAVLC P slices, more than one reference frame, multi-slice pictures, POC type 1 for a non-IDR picture, runtime resolution change, and DMA-BUF pixel content, where only the description is checked.
- VA-API encode is verified for H.264 NV12 1280x720 with `VAConfigAttribLowLatency`, `max_num_reorder_frames = 0`, `num_ref_frames = 1`, an infinite GOP and IDR on request. An ffmpeg decode of the 30-frame IPPP stream gives luma PSNR min 45.2 dB, mean 50.0 dB. The encoder's DMA-BUF import is verified on `renderD129` by `crates/lumen-encode-vaapi/tests/dmabuf_import.rs`, which imports a DMA-BUF that VA-API exported, with the AMD tiled modifier `0x0200000000000901` and two planes, and gets an IDR out of it. Intra-refresh is not implemented.
- HEVC encode and decode are not implemented. Only H.264. The capability bits for HEVC and AV1 exist but no codec implements them.
- Vulkan Video, NVENC, and NVDEC are not implemented. The NVIDIA GPU is present but has no VA-API encode.
- No low-power client tier (Celeron N4020 class) is available. Tier B cannot be tested.
- No 4:4:4, 10-bit, or HDR encode or decode path exists.

## Protocol and crypto

- **snow `risky-raw-split` (D21).** Key derivation uses a feature whose name marks it as risky. `Handshake::finish` calls `dangerously_get_raw_split` and HKDFs the split output, which is widely done and sound for this construction, but the handshake hash is not bound into the derivation (O-3). This is the main crypto risk. It needs an audit or a snow version with a stable key-export call.
- **Pairing is enforced** (D52). The host keeps the clients it trusts in a store file and refuses a client it does not trust unless the client answers the six-digit pairing code. The client proves ownership of its identity key by signing a host nonce, and `HelloAck.paired` reports the truth. The pairing code is bound to one handshake attempt (D53).
- **AEAD is negotiated** (O-2, D61). The capability bitmap travels inside the Noise handshake, so the cipher is settled before the first control record. A peer without AES-NI gets ChaCha20-Poly1305.
- **`NoiseTransport` is gone** (O-4). The dead type was deleted.
- **The audio has a key of its own** (D64). The video sender and the audio sender would otherwise share a key and a counter, which is a nonce reuse.
- **Media encryption is wired.** Media datagrams are sealed by `MediaSender::packetize` and opened by `MediaReceiver::on_datagram`, with `seq` in clear as the AEAD counter and AAD (D34, D41).
- **Media header size.** The header is 42 bytes and carries `session_id` and a 64-bit `seq` (D34). `docs/protocol.md` section 3 now describes the same layout (O-5).
- **Fuzzing exists.** Twelve targets under `fuzz/fuzz_targets/`, each run for 60 s, with four crashes found and fixed (an overflow in `is_last_slice`, an out-of-range slice descriptor, a wrong FEC recovery and an overflowing coefficient index) and no open panics. Crash-replay passes on the fixed code. The target list is in O-20.

## Transport

- **FEC and loss tests.** FEC recovery is unit-tested with simulated loss, and the `tc netem` loss and jitter sweep at 0.5 %, 2 % and 5 % loss with 10 ms jitter has been run: `scripts/sweep-loss.sh` produced the curve in `artifacts/m2/curve.csv`, with the merged report of each level in `artifacts/m2/loss-0.005.json`, `artifacts/m2/loss-0.02.json` and `artifacts/m2/loss-0.05.json`. The curve is flat: the same number of frames is presented at every level, there are no decode errors at any level, and the FEC absorbs the loss. The bandwidth-cap sweep has not been run.
- **The FEC policy is adaptive** (O-17, D59, D60). The parity level follows the measured loss, and the block size follows the level.
- **The estimator drives the encoder** (O-18, D62). The client's link feedback feeds it and its target rate reaches the encoder's constant bitrate.
- **The NACK path is bounded** (O-19, D63). The deadline is the frame's capture timestamp plus 1.5 frame intervals. No measured run has needed a NACK, because the parity rebuilds the frame first; see O-26.
- **The FEC recovery counter overstates the loss** (O-26). The counter counts every frame that the parity rebuilt, including the ones where the data slice was only late, so the loss curve reads far worse than the link was.
- **Pacing.** The token-bucket pacer is unit-tested. It has not been measured against a real link, and `send_paced` sleeps on the calling thread, which is now the dedicated send stage (O-10).
- **Socket options.** `SO_PRIORITY` and DSCP are set by `SocketOptions` but the effect is not measured.

## Audio

- The realtime callback uses `std::sync::Mutex` (D25). No underrun was measured in the wired session: `artifacts/m4/e2e.json` records `audio_underruns` zero.
- Playback through PipeWire is tested against the live daemon, and the audio path is now wired into the host and the client (D64 to D66). The host creates a PipeWire virtual sink for the session, captures it, encodes it as Opus and sends it on a socket of its own; the client reassembles it, places it against the video clock and plays it.
- The A/V skew is measured as the error in the alignment (O-31), not as a round-trip latency. Nothing has been played on hardware speakers, and no round-trip audio latency has been measured.

## Environment limits

- Xvfb tests start the server with `-displayfd 1`, so the display number is assigned rather than guessed. Earlier runs used fixed numbers (`:77`, `:93`) and collided with each other. Display-dependent tests skip with a printed reason when the variable is absent.
- Sway and Xwayland runs use software rendering (pixman or gles2 on llvmpipe or RADV). They are not representative of a physical compositor.
- No physical eDP panel was used. Every display result is from a headless or virtual output.
- Netem must be applied with `ip netns exec NS tc`. The form `ip -n NS tc` is invalid.
- PipeWire portal consent cannot be granted unattended on the first run, and restore tokens (M6.3) depend on PipeWire capture landing.
- Host load from other builds has shown up as scheduling lateness of up to 4.5 ms in the client. Latency numbers measured while the machine was busy are not reliable, so record the load with every measurement.
